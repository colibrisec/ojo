# ojo: planned work

Engineering backlog for expanding scanner functionality, in suggested build order. Excludes `--exit-code`/severity thresholds (handled at the CI/Actions layer, not in ojo) and rpm image support (owned separately).

Each item lists the approach, files touched, new dependencies (if any), and open decisions that need a call before starting. This is a plan, not a commitment to a timeline.

## Medium effort

### New ecosystem parsers, as many as reasonably possible — ✅ shipped

Same pattern every time: implement `manifest.Parser` (`Match`, `Parse`), register in `manifest.parsers` (`internal/manifest/manifest.go`), add a `model.Ecosystem` constant, write a fixture + test mirroring `manifest_test.go`. The real cost differences are (a) whether the format needs a new dependency and (b) whether it's a fully-resolved lockfile (cheap, accurate) or a source manifest with placeholders/inheritance (has a real ceiling, same shape as the `requirements.txt`-pinned-only precedent).

All six tiers below shipped. Every OSV ecosystem string was verified end-to-end against the live API with a real known-vulnerable package+version before being committed (not just unit-tested) — see the commit history for the actual CVEs each one turned up. Cross-manifest dedup also landed (`manifest.Discover` now dedupes by name+version+ecosystem across files, since PyPI alone has three sources now).

OSV ecosystem strings below are **verified against the live API** with a known-vulnerable package+version each, not assumed — getting one wrong means silent zero-results, the worst failure mode for a security tool.

**Explicitly out of scope, not just deferred:**
- `build.gradle`/`build.gradle.kts` (Groovy/Kotlin DSL, not data — meaningfully harder than any of the above; `gradle.lockfile` above covers the same ecosystem without this cost).
- **CocoaPods (`Podfile.lock`)** — checked OSV's schema directly: there is no CocoaPods ecosystem defined at all. Not a parsing-effort problem; there's nowhere to send the query regardless of how well `Podfile.lock` gets parsed. Only revisit if OSV adds one.
- **Scala/sbt (`build.sbt`)** — no dedicated Scala ecosystem either, but not needed: Scala libraries publish under Maven coordinates (e.g. `com.typesafe.akka:akka-http_2.13`), so the existing `Maven` ecosystem support already covers them correctly (verified live). The actual blocker is identical to Gradle's: `build.sbt` is a Scala program, not data. The opt-in [`sbt-dependency-lock`](https://github.com/stringbean/sbt-dependency-lock) plugin generates a JSON lockfile that would sidestep this the same way `gradle.lockfile` does — worth adding as its own small item *if* that plugin's adoption is common enough to matter; it's meaningfully less standard than Gradle's built-in locking, so verify real-world usage before investing.

### Ignorefile / risk acceptance (`.ojoignore`) — ✅ shipped

Every finding used to fail a scan forever — no way to accept a risk and keep CI green. Trivy (`.trivyignore`), Grype (`.grype.yaml`), and Semgrep (`.semgrepignore`/`nosemgrep`) all have this; now ojo does too.

- **Key**: rule/CVE ID + path glob — a Finding matches on its vulnerability's `ID` or any `Aliases` entry (so a `GHSA-...`/`PYSEC-...` alias works, not just the CVE), an Issue on its `RuleID`. Path is matched against the finding/issue's path relative to the scan root.
- **Format**: `.ojoignore` in cwd (or `--ignore-file path`), plain text, one entry per line — `<id>  <path-glob>  # reason (expires: 2026-12-31)`. Reason required (parse error if missing, same "explicit input error, not silent no-op" policy as `.ojo.yaml`); expiry optional — an expired entry stops suppressing (finding reappears) rather than erroring the scan.
- **Files**: `internal/ignore/ignore.go` (`Load`, `Rule.Matches`, `Apply`), wired into `cli/fs.go`/`cli/image.go` right after each scanner's findings/issues are assembled, before the format/`-g` branch and before the exit-code check — so a suppressed-only scan exits 0.
- **No new dependency** — stdlib `path.Match` for the glob (not `path/filepath.Match`: verified on Windows that `filepath.Match`'s separator is OS-dependent, so `*` silently spans `/` there; `path.Match` always treats `/` as the separator regardless of OS — caught by a real test run on this Windows dev machine, not assumed), stdlib `bufio`/`time`/`regexp` for parsing.
- **Resolved open decision**: SARIF gets suppressed results natively (`suppressions: [{kind: "external", justification: <reason>}]`, still present in `results[]` — the SARIF spec's own mechanism for exactly this). Every other format (`table`/`json`/`sbom`/`-g/--gitlab`) omits suppressed findings/issues entirely, no trace. `report.Report` carries `SuppressedFindings`/`SuppressedIssues` (`json:"-"`) so JSON output is unaffected regardless.
- Verified end-to-end through the built binary against a real vulnerable `django==3.2.0` in `requirements.txt` and a live OSV query, not just unit-tested: `table`/`json` correctly omit the ignored CVE while surfacing the other 37 real ones on the same package; `sarif` includes all 38 as results with only the ignored one carrying a `suppressions` entry.
- Tests: `internal/ignore/ignore_test.go` (load/parse success and every error path, `Rule.Matches` incl. expiry and the `*`-does-not-cross-`/` case, `Apply`'s partial-suppress/full-drop/alias-match/issue/root-relative-path cases) and `internal/report/sarif_test.go`'s `TestSARIFSuppressionsAreNativelyFlaggedNotOmitted`.
- Documented in `docs/guide/configuration.md` (new "Risk acceptance (`.ojoignore`)" section) and `docs/reference/cli.md` (`--ignore-file` on both `fs` and `image`).

### SARIF output (`-f sarif`) — ✅ shipped

- `internal/report/sarif.go`: hand-written SARIF 2.1.0 structs + stdlib `encoding/json`, no new dependency.
- **Validated against the official schema, not just eyeballed**: fetched `oasis-tcs/sarif-spec`'s actual schema file (note: it lives at `sarif-2.1/schema/sarif-schema-2.1.0.json` on the `main` branch — several commonly-cited URLs for this file, including the one initially used here, point at a stale `master`/`Schemata/` path that 404s) and ran a real scan's output through `jsonschema.Draft7Validator` — confirmed valid.
- Rules are deduped by ID across results (two findings citing the same CVE produce one `rules[]` entry, two `results[]` entries). Severity maps CRITICAL/HIGH→`error`, MEDIUM/MODERATE→`warning`, LOW/INFO→`note`, UNKNOWN→`warning` (not silently dropped/hidden). `Finding` locations (package-level, no line number) correctly omit `region`; `Issue` locations include it when `Line > 0`.
- Wired into `cli/fs.go` and `cli/image.go`'s `format` switch alongside `json`/`sbom`. Documented in `docs/reference/cli.md` and `docs/guide/configuration.md` (with a copy-pasteable `github/codeql-action/upload-sarif` snippet).

## Bigger commitments

### SAST beyond Go — Python ✅ shipped, JS/TS ✅ shipped, PHP ✅ shipped, Ruby ✅ shipped, Java ✅ shipped

Python shipped via `gotreesitter` (`github.com/odvcencio/gotreesitter`), a pure-Go tree-sitter runtime — no cgo, cross-compilation unaffected (verified: `CGO_ENABLED=0` builds for `linux/arm64` and `darwin/arm64` both succeed). This was not the first choice tried:

- `go-python/gpython` (mature, pure-Go, BSD-3) was evaluated first and **rejected after verification**: its parser cannot parse f-strings, the walrus operator, or `match` statements — confirmed with a real test program, not assumed. Since unparseable files are silently skipped (same policy as Go), shipping on gpython would have meant silent near-total under-coverage on real modern Python, the exact "silent zero-results" failure mode this file already warns about for OSV ecosystem strings.
- `gotreesitter` was verified the same way before adopting it: a test program confirmed it correctly parses f-strings (including interpolation as a distinct node — the structural signal the SQL/command-injection rules rely on), walrus, `match`, and type hints. It works by loading grammar tables extracted from upstream `tree-sitter-python`'s actual C source, reimplementing only the runtime/query engine in Go — not a from-scratch grammar reimplementation. Real caveat: the project is young (first commit ~2026-02, 543 stars at adoption time), a genuine risk tradeoff versus a decade-hardened cgo binding, accepted deliberately in exchange for keeping the no-cgo build story.
- Rules live in `internal/sast/python.go` as compiled tree-sitter queries (11 rules — see `docs/guide/scanner/sast.md`), curated against [semgrep-rules](https://github.com/semgrep/semgrep-rules)' Python ruleset as a reference for which patterns matter, not by executing semgrep's rule engine (that was explicitly considered and declined — see decision history in this session).
- `internal/sast/scanner.go`'s `rule` struct was **not** generalized into a shared multi-language shape — Python got its own parallel `pyRule` type and rule list instead. Two languages didn't justify the abstraction; revisit if a third language lands.

JS/TS/TSX shipped the same way, reusing `gotreesitter`'s javascript/typescript/tsx grammars — the parser choice wasn't re-litigated, but the "verify, don't assume" step was repeated: a test program confirmed all three grammars parse optional chaining, nullish coalescing, template literals, async/await, destructuring, private class fields, BigInt, dynamic import, decorators, generics, `as`-casts, and JSX (in both plain-JS and TSX files) with zero parse errors, before any rule was written.

- `.tsx` gets its own grammar (`TsxLanguage()`), not shared with plain `.ts` — confirmed directly that compiling a JSX-referencing query against the `typescript` grammar fails (`unknown node type "jsx_attribute"`), i.e. plain TypeScript's symbol table genuinely has no JSX support, this isn't a naming convention to just reuse.
- Confirmed the three grammars share identical field names/node shapes for the core JS subset (`variable_declarator`, `call_expression`, `member_expression`, `binary_expression`, etc.) — the same query source compiles against all three, so most rules are one query compiled three times (`mustTriQuery`) rather than three hand-written variants.
- Rules live in `internal/sast/javascript.go` (11 rules — see `docs/guide/scanner/sast.md`), curated against semgrep-rules' javascript/typescript rulesets the same way Python's were.
- **Bug caught during this work, worth remembering:** `Node.Text(source []byte)` slices into `source` by byte offset; passing `nil` for `source` silently returns `""` for any non-root node instead of panicking or erroring. Three call sites (JS's `+`-concatenation check, JS's `req`-root-identifier check, Python's `.format()` check) initially passed `nil` and silently never matched — caught by a targeted regression test that isolated each dynamic-string branch, not by the broader fixture tests (which happened to only exercise the template-literal/f-string branches). Always pass real source bytes to `.Text()`; a "no matches" result from a query-based rule is not proof the pattern is absent.

PHP shipped the same way: a test program confirmed `gotreesitter`'s php grammar parses enums, readonly properties, named arguments, the nullsafe operator (`?->`), match expressions, attributes (`#[...]`), union types, first-class callable syntax (`strlen(...)`), arrow functions, spread in calls, and constructor property promotion cleanly, before any rule was written.

- Single-quoted PHP strings are node type `string`; double-quoted (interpolated or not) and heredocs are `encapsed_string`/`heredoc` — this wasn't obvious from the language and was confirmed by dumping the parse tree before writing the dynamic-string check (`phpIsDynamicString` in `internal/sast/php.go`), same "verify the shape, don't assume" habit as the field-name checks for JS/Python.
- Rules live in `internal/sast/php.go` (10 rules — see `docs/guide/scanner/sast.md`), curated against semgrep-rules' php ruleset the same way. Notably includes `php-preg-replace-eval-modifier` (the historic `/e`-modifier RCE) and `php-lfi-include` (dynamic `include`/`require`), which don't have a direct analogue in the Go/Python/JS rulesets — PHP-specific classes of bug.
- `php-sql-injection` deliberately covers only `->query(`/`->exec(` (PDO/mysqli OOP style), not procedural `mysqli_query()`/`mysql_query()`/`pg_query()` — different argument signatures per function, and OOP is the dominant modern idiom. Add the procedural forms if they turn out to matter.
- Re-applied the `.Text(nil)` lesson from the JS/TS work above: every `.Text()` call in `php.go` passes the real source buffer; grepped for `.Text(nil)` before calling this done, found none.

Ruby shipped the same way: a test program confirmed `gotreesitter`'s ruby grammar parses safe navigation (`&.`), pattern matching (`case/in`), endless methods, keyword arguments, hash shorthand, heredocs, backticks/`%x{}` subshells, and numbered block parameters (`_1`) cleanly, before any rule was written.

- Rules live in `internal/sast/ruby.go` (10 rules — see `docs/guide/scanner/sast.md`), curated against semgrep-rules' ruby ruleset the same way. Includes two Rails-specific classes with no analogue elsewhere: `ruby-mass-assignment` (`params.permit!`, a strong-parameters bypass) and `ruby-open-redirect` (`redirect_to` fed from `params`/`request`).
- **A second instance of the JS/TS `.Text(nil)` mistake happened here, worth remembering harder this time:** `hasDescendant` (a helper defined in `php.go`, shared across files) hardcoded `phpLang` inside `c.Type(phpLang)` regardless of which language's node it was actually walking. Called from Ruby's `rubyIsDynamicString` on a Ruby `string` node's `interpolation` child, it silently looked up Ruby's numeric symbol ID in *PHP's* symbol table — and got lucky for the backtick/subshell case (fired correctly) but silently failed for the plain-string-with-interpolation case (`ruby-sql-injection` didn't fire on `User.where("...#{x}...")`), because the same wrong-language lookup landed on a different (wrong) name for a different symbol ID. Caught by the full fixture test, not a targeted one — this time. Fixed by giving `hasDescendant` an explicit `*gts.Language` parameter; added a dedicated regression test (`TestRubySQLInjectionViaStringInterpolation`) so it can't silently regress. **The generalizable lesson:** any helper shared across `python.go`/`javascript.go`/`php.go`/`ruby.go` that touches a `*gts.Node` needs its language passed in explicitly — never hardcode one language's global inside a "shared" helper, and grep every shared function for a hardcoded `xxxLang` before calling a new language integration done.

Java shipped the same way: a test program confirmed `gotreesitter`'s java grammar parses records, sealed interfaces/`permits`, switch expressions (`->`), text blocks (`"""`), `var`, lambdas, try-with-resources, and `instanceof` pattern matching cleanly, before any rule was written.

- Rules live in `internal/sast/java.go` (9 rules — see `docs/guide/scanner/sast.md`), curated against semgrep-rules' java ruleset the same way. Includes `java-xxe` (flags `DocumentBuilderFactory`/`SAXParserFactory`/`XMLInputFactory.newInstance()` unconditionally, since XXE hardening is an opt-in a simple query can't verify the absence of) and `java-tls-trust-manager-bypass` (flags any custom `X509TrustManager`/`HostnameVerifier` implementation, same unconditional-flag reasoning) — enterprise-Java-specific bug classes with no direct analogue in the other languages' rulesets.
- Re-applied both lessons from the Ruby work above before calling this done: grepped `java.go` for `.Text(nil)` (none), and grepped every shared cross-language helper (`hasDescendant`, `nameLooksSecret`) to confirm none of them hardcode a specific `*gts.Language` — `java.go` always compiles its own queries against `javaLang` and passes it explicitly to every `.Type()`/`.Text()` call.
- Java's `+` string concatenation is the only "dynamic string" signal needed (unlike Python/JS/Ruby/PHP, there's no interpolation syntax to also check pre-text-blocks) — `javaIsDynamicString` is correspondingly the simplest of the five language's dynamism checks.

Everything beyond Go/Python/JS/TS/TSX/PHP/Ruby/Java is still out of scope — evaluate the next language's candidate parser from scratch the same way, don't assume gotreesitter's grammar table for it is as solid as these are without testing it.

### SAST: parity with Semgrep/SonarQube — phase 1 (taint tracking) shipped for all six languages, phases 2-4 not started

Four separate gaps, requested together, sequenced because each is independently a real chunk of work and doing all four blind in one pass wasn't going to produce anything reviewable:

1. **Intraprocedural taint tracking — ✅ shipped, all six languages.** `internal/sast/taint.go` (Go, `go/ast`-based) and `internal/sast/taint_ts.go` + per-language glue in each language's own file (Python/JS/TS/PHP/Ruby/Java, tree-sitter-based, same idea generalized over the parse tree) — per-function-body pass tracking local variables assigned from a recognized taint source, propagated through concatenation/interpolation/further assignment/a wrapping call's arguments. Wired into `*-open-redirect`/`*-path-traversal`/`*-command-injection`/`*-sql-injection` wherever the rule already had an argument to inspect (all four for Go/Python/JS/Ruby/Java; PHP got `php-command-injection`/`php-sql-injection` only — `php-open-redirect` is a `header()`-text-substring rule taint tracking doesn't fit, and PHP has no `php-path-traversal`/needs none for `php-lfi-include`, see `docs/guide/scanner/sast.md`) — closes the "request data hidden behind one local variable" false negative that was the single most-repeated caveat in that doc's ceiling section, now across every language, not just Go. Every tree-sitter node-shape assumption (which node types are function/method/lambda/closure boundaries, that all of them expose their body via a field named `"body"` even for expression-bodied arrows/lambdas, `left`/`right` field names on assignment nodes) was verified against real parse trees before writing the rule against it — this project's usual "verify, don't assume" discipline, same as every previous language-onboarding entry in this file. Ceiling, same across all six: linear source-order pass, not a real CFG (branch-insensitive); doesn't cross function calls (a value passed to a helper and returned tainted isn't tracked — `TestGoTaintDoesNotCrossFunctionCalls` pins this for Go, same behavior unverified by a dedicated test on the other five); env-var-source detection is a raw source-text prefix check, not structural — fine for one or two shapes per language, would need to become structural if that list grows.
2. **Custom rule DSL — ✅ shipped, raw tree-sitter queries not Semgrep-style metavariables.** `internal/customrules`: users write rules in YAML (`id`/`language`/`severity`/`title`/`message`/`query`), one rule per `.yaml`/`.yml` file, loaded from `--rules-dir` (default `<path>/.ojo/rules`) and run alongside the built-in rules whenever `sast` is in `--scanners`. Two scope decisions made explicitly rather than defaulted, both confirmed with the user before building (this was flagged in an earlier version of this note as a decision worth surfacing, not silently picking):
   - **Pattern language: raw tree-sitter queries, not Semgrep-style `pattern: eval($X)` metavariables.** The friendlier syntax would need a real pattern-string-to-query compiler (parse a snippet as source, walk its AST, turn metavariable identifiers into captures) — a genuine subsystem, not a least-effort pick. Raw queries reuse the exact same query engine every built-in rule already uses (`gts.NewQuery`), so a custom rule is exactly as accurate as a built-in one, with zero new matching logic to maintain. Tradeoff: authoring a rule means knowing tree-sitter query syntax, not writing a code snippet — every existing built-in rule's query in `internal/sast/*.go` doubles as a copyable example.
   - **Languages: the five gotreesitter-backed ones only (Python/JS/TS/PHP/Ruby/Java) — no Go.** Go's built-in rules are hand-rolled `go/ast` predicates with no query layer to hang a YAML-driven rule off of; a Go-covering custom-rule mechanism would need an entirely separate pattern-to-`go/ast`-matcher, doubling the architecture for one language's worth of coverage. Not attempted.
   - One required convention beyond valid query syntax: the capture used for a finding's location must be named `@match` — enforced at load time (a query with no `@match` capture is a load error, not a silently-empty rule). `Load` validates every field (known language, known severity, non-empty query, `@match` present, no duplicate rule IDs across files, `yaml.Decoder.KnownFields(true)` on unrecognized keys) before the rule set is considered loaded — a bad rule fails the whole scan immediately rather than silently doing nothing, same "explicit input error, not silent no-op" policy as `.ojo.yaml`'s `--config`.
   - Tests: `internal/customrules/customrules_test.go` (11 cases: missing/empty dir, valid load, every validation failure mode, duplicate ID, actual scan producing a finding, no-rules scan). Verified end-to-end through the built binary too (a real `.ojo/rules/*.yaml` file firing during `ojo fs --scanners sast .`, plus both the malformed-rule and missing-explicit-`--rules-dir` error paths) — not just unit-tested in isolation.
   - Documented in `docs/guide/scanner/sast.md` (new "Custom rules" section, with a full example rule) and `docs/reference/cli.md` (`--rules-dir`).
3. **Rule volume — started, eight new-CWE gaps shipped, plus three rounds extending existing rules with missed sinks/shapes.** Mechanical, no architecture blocker — pick a specific CWE gap, write it the way every existing rule was written, wire in taint tracking if the rule shape supports it. Once (2) exists, bundling YAML rule packs instead of hand-writing more Go per rule becomes an option, not before.
   - **CWE-1336 SSTI — Go/Python/JS/Ruby.** Often direct RCE, previously zero coverage. Sinks, each chosen because it's unambiguous (no false-positive risk from a same-named unrelated API): Go `text/template`/`html/template`'s `New(...).Parse(...)` chain (matched as the full chain, not a bare `.Parse(` — that name collides with `time.Parse`/`url.Parse`/`flag.Parse`); Python Flask's `render_template_string(...)`; JS `ejs.render`/`ejs.compile`; Ruby `ERB.new(...)`. PHP (Twig's sink needs type resolution ojo doesn't have) and Java (FreeMarker/Velocity sinks are multi-step, no single-node shape to match) were skipped deliberately — see the `*-ssti` bullet in `docs/guide/scanner/sast.md`'s ceiling section. Tests in `internal/sast/ssti_test.go`.
   - **CWE-943 NoSQL injection — JS/Python/PHP.** Structurally different from SQL injection: the vulnerable shape is "the whole filter argument is tainted" (`Model.find(req.body)`), not "built via string concatenation" — so these rules check `*TaintedArg` alone, no `isDynamicString` term, and correctly don't fire on the common safe idiom of a literal filter object with one tainted *value* (`Model.find({ email: req.body.email })`) since the taint predicates never look inside object/array/dict literals. Sinks: pymongo/Mongoose/MongoDB-driver `find`/`findOne`/`updateOne`/`updateMany`/`deleteOne`/`deleteMany` (plus pymongo's `find_one_and_update`/`find_one_and_delete`). Ruby skipped — Mongoid's `.where(...)` sink is already caught by the existing `ruby-sql-injection` rule, a separate rule would be pure duplication. Go/Java skipped for the same name-collision-risk-without-type-resolution reason as SSTI's PHP/Java skip. Tests in `internal/sast/nosqli_test.go`. One naming gotcha hit here: a shared package-level query var name (`mongoQueryCallQuery`) collided across `python.go` and `javascript.go` — same package, so it's a compile error, not a subtle bug, but worth remembering every new cross-language rule needs a language-prefixed var name even when the shape is identical.
   - **`SameSite=None`-without-`Secure` cookie misconfiguration — `go-insecure-cookie`/`js-insecure-cookie` extended, no new rule ID.** Deliberately Go/JS only this round, not the usual 5-6-language sweep — flagged honestly rather than forced. Modern browsers already reject a misconfigured `SameSite=None` cookie outright per spec, so this is a defense-in-depth/audit check, not "definitely exploitable." *Missing* `SameSite` entirely is not flagged (browsers default to `Lax`, a reasonable fallback — unlike missing `Secure`/`HttpOnly`, which has no equivalent safety net). Python/PHP/Ruby/Java's cookie APIs could get the same whole-literal-co-occurrence-scan treatment later; not done here for effort reasons, not because the signal isn't accurate enough. Tests in `internal/sast/samesite_test.go`, each with the `secure: true`-present negative case. This is also a marker for future rounds: after ten straight new-CWE-gap slices, the remaining high-confidence/low-ambiguity gaps are thinning out — CRLF/header injection and Zip Slip were both considered and passed over earlier for real accuracy reasons (runtime-level mitigations muddying value; cross-statement detection needed beyond what a query-based scanner does safely), and forcing either through just to keep a streak going would have lowered the bar the last ten rounds held. Extending existing rules (this round, and the command-injection/eval-sink rounds before it) is the more honest lever to reach for once new-category gaps get scarce.
   - **Missed command-injection sinks on existing rules — Python/Ruby/JS, no new rule IDs.** Lower-risk than a new CWE category since it's additive to already-proven, already-tested rules rather than new ambiguity: `py-command-injection` gained `os.popen()` (unconditional flag, same shape as the existing `os.system()` check — just widened `osSystemQuery`'s `#eq?` to `#any-of?`); `ruby-command-injection` gained `popen` (e.g. `IO.popen`) to its existing method-name list, same taint/dynamic-string gating the rule already had for `system`/`exec`/`spawn`; `js-command-injection` gained a new sink shape entirely — `child_process.spawn`/`execFile` called with an options object containing `shell: true`, which reintroduces exactly the injection risk the argument-array form of those calls exists to avoid (mirrors Python's `subprocess(..., shell=True)` check already shipped). Tests in `internal/sast/command_injection_sinks_test.go`.
   - **CWE-337/CWE-338 predictable PRNG seed — Go/Python/Ruby/PHP/Java.** A distinct anti-pattern from the existing `*-insecure-random-for-secrets` rules (which flag a weak *algorithm choice* inside a security-sounding function) — this flags an explicit *literal seed* passed to any PRNG, anywhere: `mrand.Seed(1234)`/`NewSource(1234)`, `random.seed(1234)`, `srand(1234)`, `mt_srand(1234)`, `new Random(1234)`. A fixed seed makes the entire output sequence deterministic and reproducible from source alone. Literal-only (a non-literal seed argument isn't flagged — verifying it's attacker-influenced would need the taint infrastructure, and a non-literal seed is far more often a deliberately-reproducible test fixture than a real vulnerability). No new query infrastructure needed; verified each grammar's integer-literal node type (`integer` for Python/PHP/Ruby, `decimal_integer_literal` for Java) before writing the queries, same discipline as every prior slice. JS skipped — `Math.random()` takes no seed argument, so there's no matching API to misuse. Tests in `internal/sast/prng_seed_test.go`, each with a no-arg/unseeded negative case.
   - **CWE-470 Unsafe Reflection / dynamic code loading — Ruby/PHP/Java/JS/Python.** `send(tainted_method_name)`, `call_user_func(tainted_callback)`, `Class.forName(tainted_class)`, `require(tainted_path)`, `importlib.import_module(tainted_name)` — arbitrary invocation/loading by an attacker-chosen name, a real RCE-adjacent gadget class (the mechanism behind many Rails/Ruby `send`-based RCE chains in particular). Gated on taint alone (not `isDynamicString`) across all five, because every one of these APIs is routinely called with a non-literal-but-not-attacker-controlled argument in ordinary code — see the `*-unsafe-reflection` bullet in `docs/guide/scanner/sast.md`'s ceiling section for why that distinction matters here specifically. Go skipped — no string-to-reflection primitive exists there the way it does in the other five. Tests in `internal/sast/unsafe_reflection_test.go`, each with the literal-argument negative case (`obj.send(:foo)`, `Class.forName("com.example.Widget")`, etc.) since that's the case a wrong gate would have broken.
   - **Code-execution sinks beyond plain `eval()` — Ruby/JS extended, Java got a new rule.** `ruby-eval-detected` gained `instance_eval`/`class_eval`/`module_eval`, but *string-argument form only* — the block form (`class_eval do ... end`) is ordinary, ubiquitous Ruby metaprogramming, not a vulnerability, and flagging it would have been a severe false-positive regression. Verified the grammar distinction before writing the query (string form has an `arguments` field and no `block` field; block form is the reverse) rather than assuming a name-based heuristic could tell them apart — it can't. `js-eval-detected` gained `vm.runInNewContext`/`runInThisContext`/`runInContext` (Node's own docs call the `vm` module "not a security mechanism"). New rule `java-eval-detected` for `.eval(...)` (e.g. `javax.script.ScriptEngine`), gated on a non-literal argument rather than unconditional like Python's `eval()`/`exec()` — script-engine `eval()` with a hardcoded script is a normal pattern, unlike Python's `eval()` which essentially never has a legitimate call site. Tests in `internal/sast/eval_sinks_test.go`, including the negative case proving the Ruby block form stays silent.
   - **CWE-502 SnakeYAML unsafe load (`java-yaml-unsafe-load`) and CWE-377 insecure tempfile (`py-insecure-tempfile`) — one language each, unconditional-flag rules, same shape as `java-xxe`.** Picked together because both are cheap: a single query, a single language, no ambiguity about whether the flagged API has a safe use (SnakeYAML's zero-arg `new Yaml()` constructor is unsafe by design — CVE-2022-1471 and others; `tempfile.mktemp()` has no safe usage, which is why Python's own docs deprecate it). `java-yaml-unsafe-load` initially matched any `new Yaml(...).load(...)` regardless of constructor argument, which would have false-positived on the hardened `new Yaml(new SafeConstructor())` form — caught by writing the negative-case test *before* considering the rule done, not by inspection; fixed by checking the constructor's own argument count (zero args only) rather than documenting the false positive as a known ceiling. General lesson worth repeating: when a rule can cheaply distinguish the hardened form from the vulnerable one, do that instead of writing down a false-positive as if it were an acceptable tradeoff — "flag the candidate" is for cases where the distinction genuinely isn't available (type resolution, cross-statement flow), not a default to reach for out of laziness. Tests in `internal/sast/yaml_tempfile_test.go`.
   - **CWE-918 SSRF — all six languages.** A real OWASP Top 10 category ojo had zero coverage for, and structurally identical to the open-redirect/path-traversal rules already shipped (dynamic-string-or-tainted-argument on a known sink), so it got taint tracking for free from phase 1. Sinks, deliberately narrow (curated list, not every HTTP client — see the `*-ssrf` bullet in `docs/guide/scanner/sast.md`'s ceiling section): Go `net/http` Get/Post/Head/PostForm/NewRequest(WithContext); Python `requests.*`; JS/TS `fetch`/`axios.*`; PHP `file_get_contents`/`curl_setopt(CURLOPT_URL)`; Ruby `Net::HTTP.get`/`URI.open`; Java `new URL(...)`. Tests in `internal/sast/ssrf_test.go`, one fixture per language.
   - **CWE-611 XXE — Python/PHP/Ruby, extending Java's existing unconditional-flag `java-xxe`.** Go (`encoding/xml` never resolves external entities) and JS (common XML libs don't process DTDs by default) correctly stay out of scope — see the `py-xxe`/`php-xxe`/`ruby-xxe` ceiling bullet for why each language's rule is scoped the way it is (matching that language's actual default behavior, not copying Java's unconditional-flag shape blindly). `py-xxe`: `lxml.etree.XMLParser(resolve_entities=True)`. `php-xxe`: `libxml_disable_entity_loader(false)`. `ruby-xxe`: `Nokogiri::XML::ParseOptions::NOENT` / `config.noent`. Tests in `internal/sast/xxe_test.go`. Caught one bug during this slice worth remembering: PHP's tree-sitter grammar has no `false`/`true` node types — booleans are a generic `boolean` node with text `"true"`/`"false"`, same pattern already used by `phpVerifyPeerFalseQuery`/`phpCurlSSLVerifyQuery`; writing `(argument (false))` directly panics at query-compile time (`unknown node type "false"`), which is exactly what caught it — every `mustPHPQuery` call panics on an invalid node type at package `init()`, so a bad node-type guess in *any* PHP query fails the whole binary immediately, not silently.
4. **SonarQube-style code quality — ✅ shipped.** `internal/quality`, `--scanners quality`, architecturally independent of `internal/sast` as planned (no shared taint/query infrastructure — its own small per-language function-boundary node-type sets). Scope confirmed with the user before building (metrics: cyclomatic complexity, function length, nesting depth, parameter count, and cross-file duplicate-code detection — the full set, not a smaller first slice; languages: all six from the start, not staged). Full design planned via `EnterPlanMode`/`ExitPlanMode` before any code was written, given the size — the plan file's per-language decision-point verification table became the basis for `internal/quality/treesitter.go`'s shared spec mechanism.
   - **Rules** (thresholds hardcoded, not yet `.ojo.yaml`-configurable — a natural follow-up): `quality-cyclomatic-complexity` (McCabe, threshold 10, MEDIUM), `quality-function-length` (50 lines, LOW), `quality-nesting-depth` (4, LOW), `quality-parameter-count` (5, LOW), `quality-duplicate-code` (6-line window with lock-step extension to the true block length, MEDIUM).
   - **One shared tree-sitter engine, not five near-duplicate ones** (`treesitter.go`): verified two facts hold identically across all five gotreesitter-backed grammars before writing it as a single implementation — every function-like node's parameter list is reachable via a field named `parameters`, and `NamedChildCount()` on it correctly excludes punctuation with zero per-language parameter-node-type enumeration needed at all (a nice simplification found *during* verification, not planned upfront); and the `body` field convention already relied on by `internal/sast/taint_ts.go`. Two real per-language quirks caught by verifying before coding, not by a runtime bug later: Java's `switch_label` node type is shared between `case` and `default` (needs a text-prefix check, unlike JS's distinct `switch_case`/`switch_default`), and a Ruby method with an empty body constructs no body node at all (handled as the zero case, not a crash).
   - **Cyclomatic complexity's decision-point table is scoped to common/core branch constructs, documented as a real gap, not silently exhaustive** — Python `match`, JS `for-in`/`for-of`/`do-while`, Java enhanced-`for`, Ruby `unless`/`until`, PHP `match` expressions aren't counted. `&&`/`||` detection needed an operator-field check (not a type-name match) in four of five languages, since `binary_expression`/`binary` is overloaded for arithmetic/comparison too — only Python has a dedicated `boolean_operator` node type, so it alone needed no such filter.
   - **Duplicate-code detection is deliberately line-based, not token/AST-based** — the one part of this phase that's genuinely language-agnostic, so one algorithm covers all six languages (plus anything else) instead of six separate token-stream extractors, for a real accuracy-vs-effort tradeoff specific to this metric (matches PMD CPD's/jscpd's own lexical-mode precedent, not an ojo invention). Sliding 6-line window, sha256 hash, cross-file grouping, then lock-step forward extension so what's reported is the true full duplicate length rather than the minimum window — and per-file skip-ahead once a block is reported, so one long duplicate doesn't spam overlapping findings. Textual, not semantic: a renamed variable or reordered statement breaks the match, by design.
   - Not wired into `-g/--gitlab` — GitLab's Code Quality report is a separate CodeClimate-compatible format (`gl-code-quality-report.json`) that hasn't been built; noted as a follow-up rather than silently forced into the existing four report writers.
   - Tests: one file per language in `internal/quality/`, each with a single fixture function breaching all four AST-metric thresholds simultaneously plus one clean function (asserting exact rule-ID counts, not just "something fired"), plus `duplicates_test.go` covering a real cross-file duplicate (and its correct forward extension), a trivial-repeat negative case, and a distinct-files negative case. All passed on first run across all six languages. Verified end-to-end through the built binary too, including the duplicate-extension behavior showing the true block range in the table output, not just unit-tested in isolation.
   - Docs: new `docs/guide/scanner/quality.md` (full rule table, thresholds, honest ceiling), `mkdocs.yml` nav entry, `docs/reference/cli.md` (`--scanners quality` section), `docs/roadmap.md`.

### KEV (CISA Known Exploited Vulnerabilities) enrichment

CVSS severity alone doesn't say whether a CVE is actually being exploited in the wild. CISA publishes a free, stable JSON feed (`known_exploited_vulnerabilities.json`) of CVEs with confirmed real-world exploitation — cross-referencing findings against it is a cheap, high-signal addition other scanners (Grype, Trivy) already do.

- Match each `Finding`'s ID/`Aliases` (CVE form) against the KEV catalog; add a `KEV bool` (+ `KEVDateAdded`) field to `model.Finding`.
- Surface it in every report format: a badge in `table`, the boolean field in `json` (already free since it's a struct field), a SARIF severity bump, a GitLab column.
- No new dependency for the fetch — stdlib `net/http`/`encoding/json`. Caching strategy is the open decision: fetch once per run (simplest, adds network dependency to every scan) vs. cache to `~/.cache/ojo/kev.json` with a refresh interval (same shape as the local OSV DB item below, but far smaller — worth building first as a warm-up for that one, or independently since it doesn't need the full offline-DB design).
- Open decision: does a KEV hit affect `--exit-code`/severity threshold once that lands, or purely annotate? Note the dependency on that not-yet-built flag (see `docs/roadmap.md`).

### VEX (Vulnerability Exploitability eXchange)

Not implemented (see `docs/roadmap.md`). Two independent directions — pick based on which real-world use case is driving the request, they don't have to ship together:

1. **VEX output** — emit a VEX document alongside the SBOM. Ojo has no reachability analysis, so it can only mechanically assert `affected` for every live finding, not `not_affected`; the value is giving downstream tooling/humans a standard structure to fill in real exploitability judgment, not ojo generating the judgment itself.
2. **VEX input/consumption** — read an existing VEX document and suppress findings it marks `not_affected`/`fixed`. Standards-based analogue of `.ojoignore`; likely reuses `internal/ignore`'s `Apply`/`SuppressedFindings` plumbing with a VEX-document loader instead of (or alongside) `.ojoignore`. Probably the higher-value direction of the two — ingesting someone else's exploitability assertions is more actionable than emitting ojo's own low-information ones.
3. **Format decision**: OpenVEX (simpler, purpose-built) vs. CycloneDX VEX (reuses the CycloneDX code this project already has for SBOM). Check what real-world consumers actually expect before picking — don't default to CycloneDX just because the SBOM code exists.

### Local/offline vulnerability database

Currently every scan is a live query to OSV.dev (`internal/osv/client.go`) — no offline/air-gapped mode, and no resilience if OSV.dev is unreachable or rate-limits.

- OSV publishes bulk data dumps per ecosystem (GCS bucket, `.zip` per ecosystem) — sync mechanism needs to download and store these.
- Design decisions needed: storage format (embedded DB like bbolt/SQLite vs. flat files), storage location (`~/.cache/ojo/db` following XDG conventions), update cadence/staleness policy, and a `ojo db update`/`--download-db-only`-style subcommand mirroring the pattern most scanners use.
- `internal/osv/client.go`'s `Scan()` needs a second code path that queries the local DB instead of `POST /v1/querybatch` + `GET /v1/vulns/{id}` — same output shape (`[]model.Finding`), different data source, selected via a new `--offline` flag.
- This is real infrastructure (sync, versioning, storage growth over time, corruption/partial-update handling) — size it accordingly before committing to a timeline. Only worth building if air-gapped scanning is an actual requirement, not a nice-to-have.

### Mobile app binary scanning (APK / IPA)

**This is not an ecosystem parser — it's a new target type**, comparable in size to building the container image scanner from scratch (`internal/image/`), not an incremental add. An APK/IPA is a compiled, zipped app bundle, not a dependency manifest with a package-manager database to read the way Debian/Alpine images have `dpkg`/`apk`.

Note what this *isn't*: an Android app's third-party library dependencies are already covered today if the project ships a `gradle.lockfile` (see the Maven/Gradle row above) — that's ordinary dependency scanning, already shipped. This item is specifically about inspecting the **compiled binary** itself.

**Android (APK):**
- An APK is a ZIP: `AndroidManifest.xml`, DEX bytecode, native `.so` libraries, resources.
- Realistic v1 scope, roughly in order of tractability:
  1. **Manifest/permission analysis** — parse `AndroidManifest.xml` (binary XML format, not plain text — needs a decoder, e.g. porting the logic from `androidbinary`/`apk-parser`-style tools) for over-broad permissions, exported components without permission guards, `debuggable="true"`, cleartext traffic allowed, etc. This is genuinely a **misconfiguration scanner extension** (`internal/misconfig/`), not a new scanner class — closest in spirit to the existing Dockerfile/K8s/Terraform checks.
  2. **Embedded native library fingerprinting** — identify bundled `.so` libraries (e.g. OpenSSL, FFmpeg, other C/C++ deps commonly vendored into Android apps) by hash/version signature and check them the same way `internal/image` checks OS packages. Real prior art to lean on rather than reinvent: OWASP's `MobSF` project has done exactly this fingerprinting work.
  3. **DEX bytecode analysis** (secrets in strings, obviously-vulnerable patterns) — much harder; probably out of scope even for a v1 of this v1.
- OSV's `Android` ecosystem exists but covers **AOSP/platform/kernel-level** CVEs (Android Security Bulletin), not app-level findings — not directly usable for "scan my app," more relevant to firmware/OS image scanning, a different and even more niche use case.

**iOS (IPA):**
- Meaningfully harder than APK. IPAs downloaded from the App Store are FairPlay-encrypted — static analysis of the actual executable is blocked without a jailbroken decryption step, which is a legal/ethical gray area to build tooling around. Ad-hoc/enterprise-distributed builds (no App Store encryption) are more tractable, but that's a narrower audience.
- `Info.plist`/entitlements analysis (ATS settings, exported capabilities) is the iOS analogue of `AndroidManifest.xml` misconfig checks and is realistic without touching the encrypted binary — likely the only iOS-side win worth pursuing without the encryption problem.

**Recommendation:** if this gets prioritized, start with Android manifest/permission analysis only (item 1 above) — it's a real, scoped, misconfig-scanner-shaped addition. Native library fingerprinting and anything iOS-binary-related are substantially bigger and should be separate decisions, not bundled into "add mobile support."

### AI agent / skill / MCP config scanning — ✅ shipped, 13 checks across three rounds

Resolved the open decisions by folding into the existing `misconfig` scanner rather than adding a new `--scanners` value — every check below is a config/text-shaped check with a concrete structural or lexical signal, the same shape as the Dockerfile/K8s/CFN checks already there, and `misconfig` is already opt-in (not in the default `vuln`), so no separate flag was needed.

**Round 1 — MCP server configs (`internal/misconfig/mcp.go`).** Any `.json` file is tried the same way CloudFormation already is: parsed generically, then checked for a top-level `mcpServers` key (Claude Desktop/Code, Cursor, Windsurf's convention) or a `servers` key whose filename also says "mcp" (VS Code's convention, ambiguous enough alone that it needs the filename hint — checked against the file's own basename, not the full path, so an unrelated ancestor directory named "mcp" can't false-trigger it; caught by a real test run, not assumed).
- `mcp-unpinned-launcher` (MEDIUM) — `npx`/`bunx`/`uvx`/`pipx` launching a package with no version pin. Correctly ignores a scoped npm package's leading `@` when checking for a pin.
- `mcp-shell-wrapper` (MEDIUM) — `command` is a raw shell rather than a direct binary.
- `mcp-plaintext-transport` (HIGH) — `url` is `http://` and not localhost.
- Secrets hardcoded in a server's `env` block: **not new code** — `internal/secret` already walks `.json` files, so this was expected to be free. Verified end-to-end and it wasn't: the generic-secret-assignment rule's regex matched the quoted JSON *key* (`"OPENAI_API_KEY"`) before the value on the same line, and since it only checked the single leftmost regex match, that low-entropy key match caused the whole line to be rejected before the real secret was ever considered. Fixed in `internal/secret/scanner.go`'s `ruleApplies` (`FindAllString` instead of `FindString`) — a genuine bug caught by verifying the claim instead of asserting it. Regression test: `TestScan_KeyLabelDoesNotShadowLaterSecretOnSameLine`.

**Round 1 — Skill definitions (`internal/misconfig/skill.go`).** Any `SKILL.md` (case-insensitive).
- `skill-fetch-execute` (HIGH) — `curl`/`wget`/`iwr` piped directly into a shell/interpreter.
- `skill-credential-exfil-reference` (HIGH) — a well-known credential file path co-occurring on a line with a narrow transfer-verb list.
- Hardcoded secrets in `SKILL.md`: also free via `internal/secret` (`.md` already in its extension list).

**Round 2 — the six categories explicitly requested (prompt injection, tool poisoning, self-granted permissions, hidden Unicode, MCP/tool rug pulls, cross-origin escalation), mapped to concrete static-signal checks rather than semantic classifiers:**
- `mcp-prompt-injection-language` / `skill-prompt-injection-language` (MEDIUM) — a shared phrase list (`internal/misconfig/aitext.go`'s `injectionPhraseRe`) matched against an MCP server's `description` and a skill's body: "ignore previous instructions," "do not tell the user," etc. Covers the crude, common form of both prompt injection and MCP tool poisoning (poisoning *is* prompt injection, delivered via a tool description instead of a chat message) — genuinely heuristic, evadable by rewording, real false-positive risk on legitimate text using similar phrasing. The one check in this round without a purely mechanical signal; documented as such in `docs/guide/scanner/misconfiguration.md` rather than oversold.
- `mcp-hidden-unicode` / `skill-hidden-unicode` (HIGH) — shared `findHiddenUnicode` codepoint check: the Unicode "tag" block, zero-width space/word joiner, bidi override controls, mid-text ZWNBSP. The most confident check of the round — 100% mechanical, no semantic judgment. Zero-width joiner (legitimate in emoji sequences) and the bidi *isolate* range (legitimate in modern i18n text) are deliberately excluded to keep it that way.
- `skill-broad-tool-permissions` (MEDIUM) — parses `SKILL.md`'s YAML frontmatter and flags an `allowed-tools` grant of `"*"` or an unscoped dangerous tool (`Bash`, `Shell`, `Execute`); a scoped grant like `Bash(git:*)` doesn't match. Best-effort on the frontmatter key name (`allowed-tools`) — no confirmed spec to validate against, documented as a real gap (a different field name silently means nothing to check, not an error).
- `mcp-auto-approve-wildcard` (MEDIUM) — a server's `autoApprove`/`alwaysAllow` list contains `"*"`, the MCP-side analogue of self-granted permissions: every tool call skips user confirmation.
- `mcp-remote-server-unpinned` (LOW) — any `url`-based (remote) server. This is the direct "MCP rug pull" signal: a remote server's behavior isn't pinned by the local config and can change at any time — deliberately informational/every-remote-server rather than "misconfigured," same precedent as `dockerfile-no-healthcheck` firing on a common, expected-to-be-common condition. `mcp-unpinned-launcher` (round 1) already covered the *local*-launcher half of "rug pull" (an unpinned `npx` fetch); this covers the remote-transport half.
- `mcp-cross-origin-credential` (MEDIUM) — the static proxy for cross-origin escalation: an `env` var name recognizably names a well-known vendor (curated ~10-entry table: GitHub/GitLab/AWS/GCP/Azure/Slack/Stripe/OpenAI/Anthropic/Docker) while nothing in the server's own `command`/`args`/`url` references that vendor. **What this deliberately doesn't cover**: the real multi-server attack (one compromised server's tool output manipulating the model into misusing a different, more-privileged server in the same live session) is a runtime interaction pattern across multiple connected servers — invisible in any single static config file, out of reach for a file scanner by construction, not a gap to close later with more regex.
- Also explicitly out of reach and documented as such (not silently ignored): true MCP tool poisoning via a live `tools/list` protocol response — ojo reads files, not a running MCP session, so a server serving clean descriptions in its static config but poisoned ones at runtime isn't detectable this way. `mcp-remote-server-unpinned` flags the underlying exposure; it can't see the actual drift.
- Tests: `TestMCPPromptInjectionAndHiddenUnicode`, `TestMCPAutoApproveWildcard`, `TestMCPRemoteServerUnpinnedAndCrossOriginCredential`, `TestSkillPromptInjectionAndHiddenUnicode`, `TestSkillBroadToolPermissions`, `TestSkillScopedToolPermissionsNoFalsePositive` (plus the round-1 tests) in `internal/misconfig/misconfig_test.go`. Verified end-to-end through the built binary with a real `.mcp.json`/`SKILL.md` pair exercising every check at once, including a real embedded U+200B — not just unit-tested.
- Docs: `docs/guide/scanner/misconfiguration.md` updated with all 12 checks and four new ceiling notes (phrase-list-not-classifier, no live-protocol tool poisoning, no cross-server escalation, best-effort frontmatter key).

**Round 3 — agent-framework taint-sink extension ✅ shipped, Python only.** `py-agent-unsandboxed-exec` (HIGH) in `internal/sast/python.go`: `.run(...)`/`.arun(...)` called on a LangChain/AutoGen/CrewAI-style unsandboxed-execution tool (`PythonREPLTool`, `PythonAstREPLTool`, `ShellTool`, `BashProcess`, `CodeInterpreterTool`, `LocalCommandLineCodeExecutor`) with an argument that's dynamically built or (taint tracking) request/env-derived. Reuses the existing taint infrastructure twice over — once for "is the argument tainted" (`pyTaintedArg`, unchanged) and once for a new, parallel use of `tsTaintEnv`/`tsEnclosingBody` to track "is this variable constructed from a dangerous tool class," so both `PythonREPLTool().run(tainted)` (inline) and `tool = ShellTool(); tool.run(tainted)` (through one tracked local variable) fire — the second case needed a second env-builder pass, not just reusing the tainted-value one, since "constructed from class X" and "holds tainted data" are different questions the framework already generalizes over via `tsTaintEnv`'s caller-supplied predicate.
- **Deliberately Python-only this round** — JS LangChain's tool surface uses `.invoke`/`.call` instead of `.run` and a different, less-standardized set of class names; extending there needs its own verification pass rather than guessing off the Python shape, so it wasn't attempted. AutoGen/CrewAI are Python-only ecosystems anyway.
- No import-gate requirement (unlike `py-open-redirect`'s `fileImports(root, src, "flask")` check) — the six class names are distinctive enough that a same-named unrelated class is unlikely, and a wildcard import would defeat an import check regardless.
- Tests: `internal/sast/agent_tool_test.go`, one fixture covering both matched shapes (inline constructor, tracked variable) plus two negative cases (a literal argument, an unrelated object also named `.run(...)`) — passed on first run. Verified end-to-end through the built binary (a real `PythonREPLTool().run(request.args.get(...))` snippet), not just unit-tested.
- Docs: `docs/guide/scanner/sast.md` (rule table entry, honest-ceiling bullet noting the JS gap and the class-name-not-type-resolution tradeoff).

**Still not started:** nothing — all three rounds of this item (MCP+skill misconfig checks, the six explicitly-requested categories, and the agent-framework taint-sink extension) are now shipped.

- `Config` struct: `scanners`, `format` — mirrors the flag names. Whatever severity-threshold field the CI-side `--exit-code` work eventually needs should land here too; coordinate with that work before extending the schema.
- Precedence: explicit flag > `.ojo.yaml` in cwd (or `--config path`) > built-in default, implemented per-command by checking `cmd.Flags().Changed(...)` before applying a config value — not a `PersistentPreRunE` global default swap, since `--scanners` only exists on `fs` and `--format` differs in meaning between `fs`/`image`.
- A missing default `.ojo.yaml` is silent (no override); an explicit `--config path` that doesn't exist, or an unrecognized key in the file (`yaml.Decoder.KnownFields(true)`), is an error.
- Documented in `docs/guide/configuration.md` and `docs/reference/cli.md`.
